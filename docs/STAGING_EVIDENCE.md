# Staging evidence verification

The promotion reader evaluates the PR's actual head RC SHA. It reads the fixed trusted `staging.yml` push run, its latest attempt's jobs and its exact candidate/run/attempt-named artifact. Original repository/owner IDs, event/ref/path, source SHA, conclusions, artifact availability/expiry, archive digest/size and job-attempt identity must agree. A missing, failed, ambiguous, expired or older-attempt record fails. A coincidentally named green check cannot supply this proof.

The artifact bundle contains exactly four root files: canonical `staging-evidence.json`, canonical `backend-staging-artifact.json`, canonical `backend-staging-database.json` and `SHA256SUMS`. The schema-v2 receipt binds each evidence file's filename, exact size and SHA-256; schema-v1 receipts and three-file archives fail. The descriptor records both fixed Staging image digests and safe build identity/digests. The database file contains the history/runtime proof pair described below. No raw environment or credential values belong in these files. Receipt fields include the actual artifact build SHA, candidate SHA, application/contract pins, serving revision, configuration digest, SQL execution/fingerprint references and tested counterpart versions/capabilities.

The decoder checks the archive digest before reading ZIP entries, never extracts paths, and bounds archive/member output. It rejects traversal/unexpected/duplicate entries, encrypted/unsupported entries, links, overlaps, conflicting headers, invalid checksums and extra payloads. Canonical JSON rejects hidden duplicate keys. The downloader authenticates only the fixed GitHub API request; the signed storage request receives no GitHub token, cookies or caller headers. API failures do not print response bodies or signed URLs.

Expected inputs are recomputed from immutable candidate Git blobs using the same manifest rules as the builder. Migration IDs/content hashes and desired nonsecret profile references are included. Actual configuration must be recorded in reviewed `config/environments/staging.json`; the `.example.json` file remains synthetic. Planning project/URL information alone is not an operational profile.

The trusted writer's `archiveDatabaseEvidence` helper accepts only fresh in-process results from both live provider reads. It rejects offline observations, serialized CLI output and edited live results. It produces a canonical pair, its file reference and `schemaVerification`, including both execution names, migration/history/schema/permission digests and the canonical object's digest. The file SHA-256 includes its trailing newline and is separately checked; it is not interchangeable with that object digest. See [cloud database evidence](CLOUD_DATABASE_EVIDENCE.md).

After authenticating the original GitHub run/attempt and archive, promotion validates the archived pair against the receipt, operations image, baked source/input/configuration/contract identity, exact repository/run/attempt and immutable candidate SQL baselines. Both records must be successful, ordered, from distinct executions, within that workflow's time window and observed close to receipt issuance. Pending migrations and a mismatched schema or permission baseline fail. Merely supplying hashes in a receipt is insufficient. Archived `live-api` source labels gain no independent cloud authority: this path relies on the authenticated trusted writer's artifact and reports `github-workflow-artifact`, not a new live Google read. It never grants cloud credentials to promotion/work PRs.

For equivalent docs reuse, every prior bundle must remain retrievable and authenticated. The reader walks a bounded acyclic reference chain, verifies exact archived checksums/attempts and proves that each step is a docs-only Git descendant with identical build/configuration/artifact/migration-history-schema-permission inputs. The original image SHA, deployed revision/time and image digests remain unchanged. Historical receipts need not be newly issued if their artifacts remain available: the current receipt must be fresh and must carry fresh SQL verification from its own trusted run. The database file/reference changes with those new observations; it cannot be carried forward wholesale from the earlier run. Missing/expired artifacts require rebuilding/reverification rather than waiving checks. The current RC ref is read before and after verification to catch concurrent advancement. All referenced artifact expiries and current receipt/SQL/live/manual freshness are checked again at completion, so slow remote reads cannot preserve an expired result.

Public Staging checks issue bounded GETs only to the profile's `/health/live`, `/health/ready` and `/v1/meta`. They send synthetic required metadata, no staff credentials, refuse redirects and require uncached metadata. They compare the actual build SHA, environment, revision, contract version and runtime/configuration digests with the receipt. Public health/meta does not independently attest the image or SQL permissions; those facts require the trusted rollout/schema execution record. Provider IAM, controlled SQL drift invalidation, real rollout production, backup/recovery and counterpart execution remain separate required work.

The owner validation section uses these delimiters around one JSON fence:

````text
<!-- blogpost-owner-validation:v1 -->
```json
{ ...owner's factual validation record... }
```
<!-- /blogpost-owner-validation -->
````

The record includes current/tested RC SHAs, input/configuration/image digests, actual serving revision, contract pin, date, tested counterparts, all relevant scenarios and any explicit carry-forward reference. Web identity includes its actual source/input/configuration, Staging origin, serving revision and fixed image digest. Android identity includes the signed Staging Release package ID, APK filename/size/hash, version code, signing certificate and actual source/input/configuration. Changes to those identities invalidate the manual record. Each client keeps its own contract pin plus the exact backend contract against which compatibility was verified; different compatible pins and application versions are permitted. The trusted writer must substantiate those compatibility references; syntax alone does not establish compatibility.

Each scenario requires a recorded observation; Google sign-in, membership roles, cross-client editorial work, conflict/recovery, media/withdrawal and environment/share-origin checks cannot be waived. Accessibility/upgrade can be marked unaffected only with an explanation. Duplicate/escaped duplicate JSON keys and missing or unchecked scenarios fail. No function generates a successful manual claim on the owner's behalf.

GitHub's read-only GraphQL result supplies the author or actual last body editor. That actor must be the configured human owner; a self-declared owner ID, author field alone after another editor changed the body, label or self-review cannot replace attribution. A carried-forward test preserves its real tested SHA and must link to authenticated equivalent evidence, including multi-step docs chains. A new deployment or changed inputs invalidates it. Receipt freshness is initially 24 hours, manual validation seven days, with at most five minutes of clock skew; the versioned [policy](../config/ci/evidence-policy.json) controls these bounds.

The promotion job invokes this reader with read-only GitHub permissions and no cloud/signing identity. It still ends at the explicit delivery-unavailable gate. SQL archive construction and promotion validation are implemented, while the trusted staging workflow must still collect actual provider records and publish its artifact only after the complete rollout, backup and counterpart gates. Actual-profile provisioning, live provider/identity/storage/SQL/counterpart verification and production publication/recovery must be implemented and exercised before removing that gate. The local synthetic tests and the observed GitHub body-attribution query do not establish a real staging receipt or owner acceptance.
