# Cloud Run API rollout executor

The executor in `scripts/deploy/rollout.mjs` implements candidate creation, traffic promotion, bounded observation and guarded traffic recovery for an **existing** `blogpost-api` service. It is a library under development, with simulated provider transport tests. No workflow or CLI invokes it and the normal delivery fuse remains closed. This is not evidence of an actual deployment or a complete trusted delivery pipeline.

## Inputs and trust boundary

`executeCloudRunRollout` receives an immutable-copy request containing schema version 1, a numeric `runId-attempt` identifier, candidate provenance/target and the previously deployed artifacts keyed by explicit revision name. All artifacts must use the same normalized cloud configuration, project and Jakarta region. Targets must pin Artifact Registry SHA-256 digests. Previous artifacts cover every traffic target, including tagged revisions, and the current service template. They are expected inputs, **not image attestations**; the trusted caller must authenticate them independently.

The caller supplies five mandatory adapters:

| Adapter     | Responsibility                                                                                                                                                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client`    | Scoped Resource Manager/Cloud Run reads and conditional service updates; the real REST implementation is `cloudRunRolloutClient`                                                                                                                   |
| `journal`   | Private durable versioned storage; `fileRolloutJournal` is the local implementation                                                                                                                                                                |
| `authorize` | Return `true` only after fresh, independently collected source/ancestry, image/release, backup, compatible migration/schema, IAM and operational preconditions for the requested mutation                                                          |
| `probe`     | Execute the plan's bounded read-only health/meta/public/anonymous-denial checks against the supplied origin; verify envelopes, all metadata headers and one of the expected immutable artifacts; return `{ok: true}` only for a full passing round |
| `metrics`   | Collect actual service request/5xx counts for a five-minute window; return availability, integer `requests`/`serverErrors` and millisecond `windowStart`/`windowEnd`                                                                               |

`authorize` and `metrics` remain integration interfaces for their cloud proof collectors. The [read-only HTTP probe](ROLLOUT_PROBES.md) now implements `probe` and is tested through successful observation and failed-observation rollback with synthetic transport. JSON booleans cannot replace these functions. A callback returning success is not independent evidence: the future trusted workflow must authenticate and archive the collected evidence and retain the existing independent source/image/database capability checks. The local journal checksum detects corruption; it does not authenticate a downloaded deployment archive or grant permission to restore traffic.

The probe receives no OAuth token. Its implementation must forbid redirects, cookies, authorization headers and mutable/user data operations, enforce transport/body/time limits and use only known safe fixtures. The provider-observed candidate URL must be HTTPS under `run.app`, have the exact candidate tag/service prefix and contain no credentials, path, port or query. Stable-origin probes use the reviewed baked API origin. A candidate tag is publicly reachable when the service is public; zero allocated traffic does not replace application authorization.

## Execution

1. Observe an active project and the existing settled service, explicit revision traffic and actual ready previous revisions. Empty traffic and floating `LATEST` targets fail. Validate each previous image/account/program, actual secret versions, SQL attachment and runtime configuration against its expected artifact. Compare the current revision's full supported template with the service template and refuse unsupported template fields before mutation. Generation strings remain 64-bit decimal strings.
2. Require one vCPU, 1 GiB memory, request-based CPU allocation, minimum zero and a service maximum of one or two instances. Preserve the observed revision template, annotations, service configuration, budgets, SQL and account bindings. The candidate changes only the named revision, two owned labels, image digest and existing optional source/runtime declaration variables. Configuration/secret rotation is a separate reviewed operation.
3. Persist the original sorted traffic map, previous revision image/configuration fingerprints, service UID/invariant, deterministic candidate/tag and request digest. Save an intent before any update. Run authorization, re-observe identity/configuration/generation/etag, and send `template,traffic` with the previous allocation plus a zero-percent tagged candidate.
4. Persist the provider operation name before polling it. Bound operation and routing settlement to five minutes each. Verify the actual candidate revision configuration. Require three consecutive passing candidate probe rounds within five minutes. Candidate failure retains the previous allocation.
5. Re-run authorization and fresh state checks, then update **only traffic** to 100% of the explicit candidate. Preserve prior tags at zero percent. Wait for provider routing settlement and three stable-origin probe rounds before observation.
6. Observe for fifteen minutes, scheduling probe starts on thirty-second slots. Two consecutive failing rounds, or service 5xx above 5% in a five-minute window with at least twenty requests, invoke guarded rollback. Exactly 5% and fewer than twenty requests do not trigger that threshold. Latency is not an automatic rollback signal. Missing metrics, missed observation slots or an unconfirmed final failed probe fails the result while retaining current traffic for assessment.
7. Rollback re-reads the service and every previous revision, authorizes again, then restores the recorded exact traffic map with an etag and a traffic-only update. Three passing previous-origin probe rounds are required. A healthy rollback records `rolled_back` with `success:false`; it never reports deployment success. Failed/denied rollback records the last readable desired/observed map and stops automatic writes.

The REST adapter requests a fresh short-lived token for every request. It uses fixed Google hosts, scoped resource names, no redirects/cookies, fifteen-second request deadlines, strict UTF-8 JSON and a 1 MiB response bound. Updates require an etag and explicit field masks with `allowMissing=false`. It has no service creation/deletion, generic URL, job execution, Secret Manager or database operation. Provider bodies and transport diagnostics are excluded from returned errors and journal records.

## Independent recovery and persistence

`recoverCloudRunRollout` loads the same request-bound journal in a separate invocation. It resumes a recorded operation read, or reconciles a lost response against a settled live service and a changed provider generation. It never retries the missing mutation automatically. If the previous allocation is still serving, it checks that state and leaves allocation alone. If this candidate is still serving 100%, it uses the guarded rollback path. An unknown map, changed UID/configuration, expired record, source/request mismatch or uncertain write outcome requires investigation. Successful terminal deployments cannot be replayed or automatically downgraded. An incomplete observation explicitly requires operator assessment and cannot be converted into automatic rollback by invoking this recovery function.

The local journal writes under `.local/deploy/rollouts/`, rejects links and traversal, enforces an exclusive filesystem critical section and compare-and-swap version, flushes a temporary file before atomic replacement, and verifies a bounded record checksum on load. A crashed filesystem write can leave a lock; it is never stolen because of elapsed time. Inspect process ownership and actual provider state before deliberate operator reconciliation. These local filesystem operations are not a cross-runner archive, cryptographic authorization or a guarantee against filesystem/power loss. The final workflow needs authenticated durable record transfer and a separately timed recovery job, plus reserved recovery time.

No down migration, automatic backup restoration, candidate deletion or tag cleanup occurs. Preserve previous images/revisions and the release. Backup/restore decisions must account for writes made after the backup. If live state cannot be established, use the plan's separate Console recovery procedure and reconcile the resulting record before another attempt.

## Verification and remaining work

`npm run test:deploy` exercises the real REST client with synthetic transport and a virtual clock, plus actual private filesystem persistence. Tests cover both cloud environments, full observation timing, exact split-map recovery, failed probes, threshold boundaries, unavailable/malformed metrics, lost responses, operation timeout/resumption, denied recovery, competing journal writers, configuration drift and fixed transport scope. No simulated response is presented as Google evidence.

The trusted source/release/image/backup/schema/IAM collectors, Cloud Monitoring adapter, actual-provider verification of the read-only probe, stale-descendant deployment ledger, authenticated journal archive, separately timed recovery job and actual controlled cloud rehearsal remain required. The three workflows and their credential permissions are unchanged. Existing SQL/image receipts retain their original tested provenance and do not become evidence for these new source inputs. The owner's budget decision remains estimate-only; this implementation enables no API, configures no budget and creates no paid resource.

The wire adapter follows Google's [service update](https://docs.cloud.google.com/run/docs/reference/rest/v2/projects.locations.services/patch), [service/traffic](https://docs.cloud.google.com/run/docs/reference/rest/v2/projects.locations.services), [revision](https://docs.cloud.google.com/run/docs/reference/rest/v2/projects.locations.services.revisions) and [operation](https://docs.cloud.google.com/run/docs/reference/rest/v2/projects.locations.operations) schemas. Those schemas still require validation against the actual selected provider resources before operational use.
