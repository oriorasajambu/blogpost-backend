# Cloud Build recovery implementation

Cloud Build is the manually invoked bootstrap/recovery alternative described in the [backend plan](plans/BLOGPOST_BACKEND_PLAN.md) and [Console guide](plans/BACKEND_DEPLOYMENT_GUIDE.md). Normal delivery uses the three approved GitHub workflows. The recovery path must run locked checks, disposable PostgreSQL/SDK integration and contract compatibility checks, then build/push both optimized targets from one captured commit/profile. It must not deploy or migrate a cloud database.

The [executable recipe](../cloudbuild.yaml), pinned tools image and [orchestration](../scripts/cloudbuild/recover.mjs) are authored locally. Actual Cloud Build execution, effective IAM, image publication and provider provenance remain unverified. Normal delivery remains closed. The owner's [estimate-only budget decision](CLOUD_COST_ESTIMATE.md) does not authorize provisioning or budget configuration; this increment creates none.

## Observed build context

[Context validation](../scripts/cloudbuild/context.mjs) accepts only a build UUID, environment, selected project ID and Jakarta region as routing inputs. Environment/project numbers come from [cloud project planning](../config/cloud-projects.json). Routing inputs and substitutions cannot attest execution identity. The [live reader](../scripts/cloudbuild/reader.mjs) independently reads:

1. Metadata service account email, before requesting a short-lived metadata token. It must be the selected project's `blogpost-build` account.
2. The selected Resource Manager project, including its independent numeric identity and ACTIVE state.
3. The actual regional Cloud Build record, requiring WORKING status, bounded timestamps, the custom account and an unambiguous resolved 2nd gen connected-repository SHA.
4. Its actual `blogpost-backend-manual` trigger and connected repository. The trigger must use manual invocation, root `cloudbuild.yaml`, the selected RC/main branch or exact resolved commit, and the same account/repository. Configuration can use `filename` or an explicit `gitFileSource` for that same connected repository/path/ref. Automatic event sources, inline/alternate recipes, file filters, tag sources, private pools and build secret bindings are rejected. The connected remote URL must match the configured GitHub repository.
5. The build, trigger, repository and metadata email again, rejecting changes to the verified observations.

Reads use fixed metadata/Google hosts, GET only, bounded fatal-UTF-8 responses, timeouts and no redirects/cookies. Only Google API reads receive the metadata bearer token; metadata requests use the required metadata header. Provider diagnostics and credentials are not emitted. The token stays in memory.

Explicit JSON observations are labeled `provided-json`. Only the live-reader result receives a private in-process binding. A serialized, edited or expired result cannot satisfy `requireLiveCloudBuildContext`; the observation must remain fresh within sixty seconds. This is a capability for cooperating verification code, not a sandbox against arbitrary code already executing as the builder account.

Google documents that trigger-style substitution values can also be supplied to builds submitted through the CLI. Consequently `_APP_ENV`, `COMMIT_SHA`, `REVISION_ID` and `BRANCH_NAME` are checked for disagreement, but never used as independent evidence of trusted source. See [substitution behavior](https://docs.cloud.google.com/build/docs/configuring-builds/substitute-variable-values), [Build API](https://docs.cloud.google.com/build/docs/api/reference/rest/v1/projects.locations.builds), [trigger API](https://docs.cloud.google.com/build/docs/api/reference/rest/v1/projects.locations.triggers) and [connected repository API](https://docs.cloud.google.com/build/docs/api/reference/rest/v2/projects.locations.connections.repositories).

## Reviewed Git source

[Source verification](../scripts/cloudbuild/source.mjs) requires the fresh in-process context, a clean checkout on the authorized permanent branch, matching provider SHA, exact configured GitHub origin and unchanged repository/owner identities. Real Git ancestry must place the build SHA on the currently observed authorized branch. A reviewed older ancestor can support recovery; a detached history cannot. Source trees and introduced history pass the same forbidden-path/link/collision checks used by CI.

The shared [reviewed merge policy](../scripts/ci/source-proof.mjs) requires an actual two-parent merge and a unique live GitHub merged-PR association. It checks repository IDs, route, head SHA, closed/merged state, non-draft status, absent auto-merge and the configured solo owner as merger. Main additionally requires the existing release/version/promotion tree rules. The GitHub branch, local checkout/origin and context freshness are checked again after remote reads.

Cloud Build does not synthesize a GitHub Actions event to enter that policy. The Actions wrapper retains its own exact repository/event/workflow guards. A `MANUAL` trigger record establishes trigger configuration; it does not prove who invoked this build or replace owner acceptance.

## Executable recovery pipeline

The recipe has three sequential steps, a sixty-minute build timeout and a fifteen-minute queue bound. `_APP_ENV` defaults to `UNSELECTED`; the manually invoked trigger must explicitly select `staging` or `production` in the corresponding project. Only reviewed RC/main source is accepted. A selected older recovery SHA must still be on that branch's actual Git ancestry.

| Step          | Behavior                                                                                                                                                                                                                                                                                                                           |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `capture`     | A digest-pinned Node/Git image reads the actual provider context and exact recipe, clones full public Git history into an invocation-owned workspace, checks the reviewed merge, validates the committed profile/compatibility mode and captures frozen build inputs. Existing invocation state is not overwritten.                |
| `tools`       | Builds an invocation-only tools image from the captured source. [Its Dockerfile](../docker/cloudbuild/Dockerfile) combines pinned Node/npm, Docker/Buildx and a Debian-compatible JDK 17. [Tool references](../config/cloudbuild-toolchain.json) are Linux amd64 manifest digests. The tools image is not among published outputs. |
| `check-build` | Reauthenticates context/recipe/source, creates a separate clean work branch at the same SHA for Development-only tests, runs the locked checks, verifies fresh SQL/SDK evidence, builds/smokes API and operations from the same capture, and checks final source and Docker tag identity.                                          |

The in-process reader retains the observed Build record for recipe verification. [Recipe policy](../scripts/cloudbuild/recipe.mjs) requires the expected step images, arguments, dependencies, timeouts and exact two image destinations. Modified entrypoints, extra environment/volumes, soft failures, automatic substitution mapping, extra user substitutions and unapproved artifact outputs fail. The checked-in YAML must match that model in CI. Serialized context cannot supply a trusted recipe.

Checks include `npm ci`, native metadata, source/history secret scanning, CI/build/deployment/security regressions, Prisma validation/generation, generated contract/TypeScript/Kotlin checks and Kotlin consumer tests, compatibility regressions and baseline comparisons, formatting/docs/type/unit/mock checks, disposable SDK/SQL/operator execution, compilation and all four npm dependency audits. A failed check aborts the step before publication images are built. The SQL result must bind all 52 operations, all required suites and compiled operations to the candidate's actual SHA/source digest. Its emulator/local-filesystem limitations remain explicit.

The [populated recovery rehearsal](DATABASE_RECOVERY_REHEARSAL.md) runs after the SDK/SQL suite. Its fifteen local upgrade/restore/media checks must bind the same captured source and Development runtime inputs before publication images are built. This Development migration-boundary exercise is not a cloud backup receipt or old-release compatibility approval.

Cloud Build's `images` field performs the managed push only after successful steps. It publishes `backend:build-BUILD_ID` and `backend-operations:build-BUILD_ID` in the selected Jakarta `blogpost` repository. No script invokes `docker push`, deployment, cloud SQL operations or Secret Manager. `requestedVerifyOption: VERIFIED` requests provider provenance; that setting is not proof that it was produced. The local result ends at `CHECKS_PASSED_PUSH_PENDING`. Require the terminal provider status, actual pushed digest results and verified provenance before using either artifact for recovery. See [Build configuration and image publication behavior](https://docs.cloud.google.com/build/docs/api/reference/rest/v1/projects.locations.builds).

## Completed build and signed artifact verification

The read-only [result CLI](../scripts/cloudbuild/verify-result.mjs) checks the terminal evidence after an authorized manual build. Its request JSON has exactly `buildId`, `environment`, `projectId` and `region`; these select resources rather than attest identity. Use a clean trusted verifier checkout with full Git history, the exact reviewed source commit and its committed actual environment profile. The verifier may be newer than the built commit. A reviewed recovery ancestor remains acceptable only while the live authorized branch still contains it.

```powershell
node scripts/cloudbuild/verify-result.mjs --request .local/cloudbuild-result-request.json --source-sha FULL_REVIEWED_MERGE_SHA --live
```

Supply an existing short-lived read credential as `GCP_ACCESS_TOKEN` through the process environment. The CLI does not obtain, print or persist credentials. It needs read access to Resource Manager, Cloud Build, Artifact Registry, Artifact Analysis occurrences and Google's builder public key; effective IAM has not been validated. GitHub association reads are public and never receive the Google token. No API is enabled by this command.

[The reader](../scripts/cloudbuild/result.mjs) requires a successful regional build, all three successful recipe steps, the exact two managed image results and distinct immutable digests. It verifies the selected immutable-tag Docker repository and corresponding registry image records. Expected application/contract/configuration/input metadata is recomputed from the source commit; it is an expectation, not an observation of the image filesystem.

For each digest, the reader queries one unambiguous Artifact Analysis BUILD occurrence filtered to that image and build invocation. It checks the signed DSSE payload using Node's P-256/SHA-256 verification, fetching the public key only from Google's fixed `verified-builder` KMS namespace and checking the PEM CRC32C. The decoded in-toto v1/SLSA v1 statement must bind the Google hosted builder, regional invocation, original build times, repository/configuration path, resolved Git commit, environment, approved build dependencies and image subject/digest. Unsigned occurrence mirror fields are not used as evidence. See Google's [build provenance documentation](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance), [build-type definition](https://docs.cloud.google.com/build/gcb-buildtypes/google-worker/v1) and [KMS public-key API](https://docs.cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys.cryptoKeyVersions/getPublicKey).

Fixed-host bounded GETs re-read the provider records, occurrences and public keys; changes, pagination, ambiguity and non-JSON/redirect/error responses fail. The GitHub owner-merged PR and branch ancestry are checked, with the branch and local verifier state rechecked afterward. Original build timestamps remain separate from fresh observation time. Only the unchanged in-process live result satisfies `requireLiveRecoveryResult` for sixty seconds; serialized output cannot carry that capability.

For offline diagnostics, replace `--live` with `--observations PATH`. The supplied bundle contains `project`, `build`, `trigger`, `repository`, `registry`, `images`, `occurrencePages` and `keys`. Both image and occurrence arrays use API-then-operations order. This checks consistency and signatures against the **supplied** public keys and always reports `provided-json` / `provided-public-key`. It does not authenticate Google authority, prove live reviewed-source acceptance or authorize deployment. Duplicate JSON keys and extra observation fields fail.

Local tests use real ephemeral ECDSA signatures, real temporary Git merges and synthetic HTTP responses. No actual completed Cloud Build, published image, Google signature/key response or provider permission has been verified. The checker does not establish the human invoker, effective IAM, complete SBOM/scanning, database compatibility, rollout safety, client acceptance or release readiness. Normal delivery remains closed.

## Profile and compatibility prerequisites

The manual recipe requires a reviewed **nonsecret committed** `config/environments/staging.json` or `production.json`. Neither exists yet. The private `.local/profiles/` inputs supported by local build helpers are not present in a Cloud Build clone. The recipe rejects the example profiles, another project's identity, different planned origins or an SQL region outside Jakarta. Never commit credential values: only validated resource names, audience/origins, accounts and numeric secret-version references belong in a profile. Live provider/resource verification remains required separately; schema validation does not establish that resources exist.

[The compatibility catalog](../config/contract-baselines.json) currently says `INITIAL_DRAFT` with no baselines. That mode is valid only for Staging application `0.0.0`, `publish:false` and a DRAFT contract. It explicitly reports `NOT_RUN_INITIAL_DRAFT` for supported published baselines. It cannot produce a Production recovery build or be carried into a later release version. These prerequisites are checked during capture before building the large tools image.

After actual contract publication/review, use `REVIEWED_HASHED_BASELINES` with the complete supported inventory of checked-in `config/contract-baselines/*.json` files, exact SHA-256 hashes and v1 contract versions. Every baseline is checked and compared; absent, duplicate, changed or breaking inputs fail. The candidate, catalog, baseline bytes and first-parent contract are read from immutable Git blobs. The report identifies that committed HEAD and candidate contract checksum; working-file edits cannot become source-bound evidence. The actual Git first-parent contract is compared when present, separately from supported baselines. A missing first-parent contract is recorded explicitly. [The compatibility runner](../scripts/cloudbuild/compatibility.mjs) writes its structural report under ignored `.local/`; it does not rewrite the canonical contract/report. Reviewed file hashes do not authenticate release publication or replace semantic/old-client acceptance.

## Docker workspace portability and retention

The recipe uses `npm run test:identity -- --build --compiled-operations --copy-reports`. This mode creates invocation-named disposable containers, writes only their synthetic observation JSON to their writable layer, checks their exit status, copies exact run-named reports through `docker cp`, then removes each container. Database/auth/media storage stays disposable; no named data volume or published port is created. The default local bind-report mode remains supported.

Optimized image smoke scripts travel over Docker stdin and use `--network none`, disposable credential placeholders and no runtime credential mounts. Their execution does not depend on daemon-side access to a builder's workspace path. Docker builds transfer the captured context through the Docker API. API/operations smoke checks include non-root/read-only metadata, truthful environment/source/input pairing, metadata privacy, unavailable-SQL readiness and operator wrong-environment rejection.

The tools image and test artifacts belong to the short-lived Cloud Build worker. Keep no tools image in the permanent Development inventory. Local verification removes temporary tags and trims unused builder layers while preserving npm/Prisma download mounts and saved data volumes. Docker's overlapping image/cache figures are not additive. No Windows disk compaction is required by this recipe.

## Verification and remaining work

`npm run test:ci` covers provider/source/recipe/orchestration boundaries with mock metadata/Google/Docker transports and real disposable Git histories. Synthetic credentials never leave the test transport. Tests exercise both environments, project-number aliases, malformed/oversized/redirected responses, substituted identities, alternate sources/triggers, changing observations, private in-process trust, stale context, unreviewed merges, moving branches, source changes during reads, exact recipe matching, failure before image construction and final image identity drift. The orchestration tests do not execute their simulated quality/Docker commands and do not establish a successful provider build. Real local Docker tool, SDK/SQL and optimized-image results are recorded separately in [implementation status](IMPLEMENTATION_STATUS.md).

Still required before recovery is usable:

- Supply reviewed actual nonsecret profiles and the applicable supported compatibility baselines. Verify the authored recipe on the actual Cloud Build runtime; local transport tests and a local Docker daemon do not prove provider compatibility.
- Observe the actual locked checks, disposable SQL/SDK/operator suites and both optimized images in that authorized build. Preserve the true tested source and environment provenance.
- Record actual immutable API/operations pushed digests, successful terminal build status/results and authenticated provider source/image provenance. Context verification and the local push-pending report alone prove none of those outcomes.
- Verify effective IAM, the actual manual connection/trigger, provider runtime/tool compatibility and explicit human recovery authorization in the selected project. Give the builder no SQL, Secret Manager or deployment authority. The readonly guard additionally needs its fixed project/build/trigger/repository reads; exact effective bindings remain unverified.
- Keep publication, cloud execution, populated upgrade/backup recovery, rollout, counterpart acceptance and normal release gates separate. No local test or archived proof bypasses them.
